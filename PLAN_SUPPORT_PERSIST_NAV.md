### Почему QR отложен и как его будем делать (справка на следующий заход)
Рабочий QR для приёма перевода физлицу **нельзя сгенерировать на клиенте**:
- QR СБП для приёма денег — payload `https://qr.nspk.ru/QR_ID?type=…&bank=MEMBER_ID&sum=…&cur=…&crc=…`, где `QR_ID` выдаёт НСПК, `crc` — контрольная сумма, внутри — банковские реквизиты получателя;
- для переводов между физлицами существует **персональный QR, который получатель создаёт в приложении своего банка** (сервис НСПК, запущен с ВТБ 09.06.2026: можно указать сумму и скрыть номер); плательщик сканирует и подтверждает. Т‑Банк сканирование QR получателя также поддерживает штатно.

Схема следующего захода (зафиксирована, чтобы не переобсуждать):
1. В способе **СБП** появляются поля `qr_data_url` (картинка из приложения банка) и `bank` (список ~12 популярных + «другой» своим текстом).
2. Загрузка — по образцу аватара: демо → dataURL, реал → бакет Supabase Storage (`donate-qr`); даунскейл до ~600×600 на canvas, лимит ~300–400 КБ.
3. В окне поддержки СБП раскрывается: QR ≈260 px (клик = увеличить), банк + номер + «Скопировать», фолбэк-текст. Если QR нет — подсказка автору «добавьте QR из приложения банка».
4. SQL менять не нужно: `profiles.donate_methods` — `jsonb` без CHECK (`supabase/setup.sql:473`), достаточно комментария.
5. **Зависимость:** QR-картинка — тяжёлый dataURL, поэтому перед этим заходом желательно сделать пункт 3 ниже (квота/IndexedDB), иначе демо-хранилище будет переполняться быстрее.

## 2. Сохранность демо-данных: перенос контента через смену версии

### 2.1 Причина (диагноз, подтверждён кодом)
`loadDemo()` (`supabase.mjs:411-425`): при `saved.v !== DEMO_DB_VERSION` вызывается `migrateDemo()`, который переносит **только** `DEMO_MIGRATE_PROFILE_FIELDS` + словари `software`/`arsenal`. Вопросы, ответы, комментарии, сообщения, лайки, избранное, уведомления, достижения, подписки, донаты **выбрасываются** и пересоздаются из сидов. Между сессиями версия поднялась 7 → 8 (коллаборации/контакты) — поэтому созданный вопрос исчез после перезагрузки. Скачивание файлов (`<a download>`) состояние не трогает.
Второй, независимый риск (в этот заход **не** лечим): `persistDemo()` при переполнении localStorage пишет только `console.warn` — изменения молча перестают сохраняться.

### 2.2 Что делаем
`migrateDemo(saved)` расширяется переносом пользовательского контента:
1. **Идентификация «своё vs сиды»**: сидовые id известны статически (`q0…q5`, `a1…a5`, `c1…c3`, `r1…r3`, `u-anna/u-max/u-lena/u-demo`, уведомления/достижения из сидов). Всё, чего нет в сидах, — пользовательское.
2. **Перенос по коллекциям**: `questions`, `answers`, `comments`, `messages`, `notifications`, `likes`, `favorites`, `subscriptions`, `donations`, `achievements` — пользовательские записи добавляются к новым сидам (для `likes`/`favorites`/`subscriptions` — дедуп по составному ключу).
3. **Чистка «висяков»**: ответы без живого вопроса, комментарии без живого ответа, лайки/избранное/подписки на несуществующие цели, сообщения от/к несуществующим профилям — удаляются. Профили **не** создаются из снапшота (иначе вопросы повиснут на призрачных авторах): вопрос без известного автора показываем как «Участник» (существующий фолбэк рендера).
4. **Счётчики**: у перенесённых вопросов `answers_count`/`likes_count` пересчитываются из перенесённых `answers`/`likes` (чтобы не сложить сидовые лайки с пользовательскими).
5. **Порядок**: перенесённые вопросы — после сидов, лента всё равно сортирует по `created_at`.
6. **Тост**: `demo.reseeded` переписывается честно — «Демобаза обновлена (v{from} → v{to}): ваши вопросы, ответы и настройки перенесены, демонстрационный контент обновлён».

### 2.3 Тесты
- Новый `tmp_tests/test_demo_persistence.mjs`: имитируем снапшот v8 в localStorage (свой вопрос + ответ + комментарий + лайк + избранное + сообщение + подписка + донат) → старт с v9 → всё на месте, сиды обновлены, «висяки» удалены, счётчики корректны, тост — новый текст; отдельно: перенос `open_to_collab`/`contact`/`donate_methods` (регресс v8) и фильтрация `donate_methods` до СБП/карты.
- `tmp_tests/test_demo_migration.mjs` — дополнить (v9 вместо v8), `test_moderation.mjs` — версия v9.

### 2.4 Отложено (осознанно)
Видимая ошибка при переполнении localStorage, перенос тяжёлых dataURL (аудио/аватары/QR) в IndexedDB, экспорт/импорт демо-данных — отдельным заходом, желательно **до** QR (см. 0.5).

## 3. Свечение `.nav-icon.active` (вариант «без overflow»)

### 3.1 Причина
`.main-nav { overflow-x: auto }` (`style.css:150-158`) — по спецификации `overflow-y` при этом вычисляется как `auto`, контейнер становится clip-боксом высотой ровно 40 px (высота иконок), а `--copper-glow: 0 0 12px rgba(255,140,0,.35)` даёт видимый ореол ~±18 px → сверху и снизу он **срезается прямой линией**. Тем же обрезается `.notif-badge { top:-5px; right:-5px }` (`style.css:257`) у иконки «Сообщения».

### 3.2 Что делаем
- `.main-nav`: `overflow-x: auto` → `overflow: hidden`; `height: var(--header-h)` (64 px) + `align-items: center`; убрать `scrollbar-width: none` и правило `::-webkit-scrollbar` (скролла больше нет). Clip-бокс 64 px ≥ 40 + 2·18 → ореол и бейджи помещаются целиком.
- Адаптив (чтобы на узких экранах иконки не «съезжали» под обрез): `@media (max-width: 420px)` — `.nav-icon { width/height: 36px }`, `gap: 2px`; при необходимости скрываем `title`-подсказки. Итог: 5 иконок по 36 px + зазоры ≈ 188 px — помещаются даже в 320 px.
- Проверить попутно `.tabs` (`style.css:1562`, тоже `overflow-x: auto`) и мобильные полосы на такой же подрез активного свечения; если воспроизводится — точечно добавить внутренний отступ (не меняя раскладку).

### 3.3 Проверка
- Статический CSS-тест в существующем прогоне: `.main-nav` содержит `overflow: hidden` и `height: var(--header-h)`, не содержит `overflow-x: auto`.
- Визуально: скриншот шапки до/после (сохраняем в `/home/user/nav-glow-compare.html` по образцу `help-mode-compare.html`).
